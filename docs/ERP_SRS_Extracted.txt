Purpose: define the implementation baseline, functional scope, architecture, authorization model, workflows, data, security, testing and delivery approach for an ERP portal similar to the supplied reference videos.






Purpose, Scope & Assumptions
Purpose
This SRS converts the reference product behavior into implementable, testable requirements for an education ERP. It is the baseline for development tickets, API implementation, database design, QA, senior review and release decisions.
In Scope

Domain
Baseline
Identity/access
Login, logout, password lifecycle, users, roles, permissions, audit
Student lifecycle
Enquiry, admission, student/guardian profile, documents, transfer/exit
Academics
Session, class, section, subject, syllabus, homework, timetable
Attendance
Student/staff marking, correction and summaries
Finance
Fee structures, dues, collection, receipts, discounts, expenses
Operations
Inventory, library, hostel, support/tickets
Administration
Reports, settings, imports/exports, audit
Out of Scope for Release 1
Native mobile applications; full statutory general ledger; complex third-party integrations; SaaS multi-tenancy unless separately approved.
Statutory payroll/tax compliance unless explicitly added to the approved backlog.
Assumptions
Initial architecture is a modular monolith with MySQL as system of record.
One institution/branch is assumed initially; branch-aware fields may be retained for future expansion.
Backend authorization is authoritative; frontend hiding controls is not a security boundary.
Critical writes are server-validated and transactional.

Backup / restore
Automated MySQL backups must meet RPO 24 h and be periodically restored.
